# Services — `src/services/`

> **Keep this file updated** whenever you add, remove, or significantly change a service.

All services are **static classes** — never instantiated with `new`. Initialize once at startup and call with `ClassName.method()`.

## Infrastructure / Core

| File | Class | Purpose |
|---|---|---|
| `gunService.ts` | `GunService` | GunDB wrapper. `initialize()` called in `main.ts`. Now uses a **multi-peer array** from `config.getGunPeers()` — Gun connects to all peers simultaneously. `getPeerStats()` returns `{ isConnected, peerCount, connectedCount, avgLatencyMs }`. `getDetailedPeerStats()` returns per-peer `{ url, connected, latencyMs }`. `reconnect(urls?)` accepts a single URL, array of URLs, or none (uses config) and **rebuilds the Gun instance**, so any `.on()` subscription bound to the old instance goes stale. Before discarding the old instance it **dismantles** it (detaches every chain in `root.next`, clears `root.graph`/`next`/`dup`/`tag`/`opt.peers`): callers all over the app hold long-lived chains that keep the old root reachable, so without this every reconnect leaked the entire in-memory graph — and since the watchdog's response to memory pressure *is* a reconnect, that was a runaway loop. `subscribe(path, cb)` and `map(path, cb)` now **return an unsubscribe function** — call it on teardown. `attachWireBridge(send, opts)` returns a stable `receive` that delegates through the service, and the bridge is re-installed against the fresh root on every `reconnect()`; the handle must never be re-created per instance or it would pin a discarded root. `onReconnect(cb): () => void` registers a callback fired after each `reconnect()` rebuild so Gun-bound subscribers (signaling inbox, discovery, rendezvous) can re-attach; `SignalingService` and `DiscoveryService` use it. `addPeerDynamic(url)` adds a peer to the **existing** instance via `gun.opt({peers})` — no rebuild, so it widens the pool without dropping subscriptions. Peer latency is tracked by measuring WebSocket open time. All data roots are transparently namespaced under `v3` via a Proxy. |
| `gunRelayPresets.ts` | — | Preset list of 38 public Gun relay URLs (`GUN_RELAY_PRESETS`) with labels, default peer set (`DEFAULT_GUN_PEERS`: InterPoll + gun-manhattan + gun-us), `isValidGunUrl()`, and `labelForGunUrl()` helpers. Used by Settings and ResiliencePage Gun peer management UI. |
| `storageService.ts` | `StorageService` | IndexedDB wrapper (`idb`). Stores: `blocks`, `votes`, `receipts`, `polls`, `metadata`, `encryption-keys`, `comments` (index `by-post`), `chat-messages` (index `by-room`). DB name: `interpoll-db` **v3** — the `comments`/`chat-messages` stores were added in the v3 upgrade and are the durable mirror for the social layer, which Gun cannot provide (`localStorage:false, radisk:false`). `pruneComments(max)` never drops a row with `authoredLocally && syncStatus !== 'confirmed'`, and `pruneChatMessages(maxPerRoom)` never drops an undelivered outgoing message: those rows are the only copy that exists. Receipt reads/writes now normalize to `verificationCode` while preserving legacy `mnemonic` fields for backward compatibility with existing stored data. The `metadata` store is a generic key-value bag used by many other services. The `encryption-keys` store holds `StoredEncryptionKey` entries keyed by `id`. |
| `websocketService.ts` | `WebSocketService` | WebSocket peer connection to the relay server. Handles reconnection (exponential backoff, infinite retries), peer discovery, server list sharing, and message queuing when disconnected. Subscribe to message types via `.subscribe(type, callback)`. Also supports encrypted chat room message relay: `broadcastChatRoomMessage(roomId, data)` sends an opaque encrypted blob via the relay, and `subscribeToChatRoom(roomId, callback)` receives them with per-room multiplexing. At startup/reconnect it also publishes and consumes signed Gun discovery announcements via `DiscoveryService`, so known servers can be sourced from `v3/server-config/discovery` in addition to WSS `server-list` broadcasts. Known-server entries track source (`local`, `peer`, `gun`) and explicit trust metadata (`signatureValid`, `lastVerifiedAt`, `expiresAt`) without inferring signature trust from labels/source strings; local self-seeded entries are stored unsigned by default. Peer counts now fall back to observed `peer-addresses` broadcasts when `peer-list` is stale or omits the sender, and they represent **other peers only** (so `0` is valid when no one else is connected). On relay `PEER_ID_TAKEN` errors, the client rotates to a new ephemeral peer id and re-registers automatically. Incoming `server-list` entries are only accepted when the relay envelope passes `IntegrityService.verifySealedPayload()` and endpoint protocol safety checks. `broadcast()` is async and automatically attaches proof-of-work for content messages (via dynamic import of `PowService`), then seals the message with `IntegrityService.seal()` (hash, signature, hashcash PoW, replay nonce) before sending — seal failure drops the message. `sendRaw(message)` sends a raw message bypassing PoW/broadcast wrapping. |
| `discoveryService.ts` | `DiscoveryService` | Relay discovery registry rooted at `v3/server-config/discovery`. Publishes signed relay announcements (`nodeId`, `peerId`, `websocket`, `gun`, `api`, `capabilities`, `timestamp`, `ttlMs`, `signerPubkey`, `signature`), verifies Schnorr signatures before accepting, enforces TTL expiry and max-entry caps, and exposes normalized validated discovery entries for other services. Bootstrap discovery now prefers a bounded relay `/db/search` snapshot (avoids broad Gun graph flood on startup); live Gun `map().on` subscription is explicit-only via `initialize({ subscribeLive: true })`. Announcements include a `capabilities` list; nodes that can accept direct WebRTC connections advertise `webrtc`, and `MeshService` uses `signerPubkey` from those entries as a Gun-addressable dial target. **Rendezvous ("DGA") extension:** `publishRendezvous()` / `subscribeRendezvous()` mirror the same signed announcement under a rotating soul path `v3/server-config/rdv/<soul>` where `<soul>` is deterministically derived per 6h epoch by `src/utils/rendezvous.ts` (`activeSouls()` covers current ±1 epoch). Every node with the shared protocol salt derives identical souls with no coordination, so peers reconverge even when the fixed `discovery` path is censored/flooded. Rendezvous records pass the **same** `normalizeAndValidate()` signature/endpoint/TTL gate — a forged record at a guessed soul is dropped before it reaches `addKnownServer`, so this does not widen the forged-graph attack surface. **Sybil gate:** every announcement (discovery + rendezvous) now also carries a hashcash `pow` nonce over its signature (`POW_DIFFICULTY_BITS = 16`, `computePow`/`verifyPow`); `normalizeAndValidate` rejects announcements without sufficient PoW, so flooding a soul with many fake-but-signed identities costs real work per identity. |
| `broadcastService.ts` | `BroadcastService` | Cross-tab sync via `BroadcastChannel('interpoll-sync')`. Same message types as WebSocket. Both channels are always wired in parallel in `chainStore`. |
| `webrtcService.ts` | `WebRTCService` | WebRTC P2P DataChannel service — the **mesh transport** wired in as a third fan-out alongside `BroadcastService`/`WebSocketService` in `chainStore`. Connections are keyed by an opaque `remoteId` (relay peerId on the WSS tier, signing pubkey on the Gun tier); each remembers a `reply` `SignalTarget`. Signaling is delegated to `SignalingService` (not hardwired to WSS). Exposes `connectToPeer(remoteId, target)`, `broadcastToAll(type, data)`, `onMessage(type, cb)`, `onPeersChange(cb)`, and **manual offline signaling** `createManualOffer()` / `acceptManualOffer(bundle)` / `acceptManualAnswer(bundle)` (non-trickle ICE so all candidates ship inside a single base64 bundle). Opt-in/out via `localStorage('interpoll_mesh_enabled')` (separate from the snapshot-sync `interpoll_webrtc_enabled` flag). Google STUN for NAT traversal; degrades gracefully. |
| `signalingService.ts` | `SignalingService` | Tiered WebRTC signaling abstraction. Picks the best live channel: (1) **WSS relay** — legacy `rtc-offer/answer/ice` wire format, routed by ephemeral peerId; (2) **Gun inbox** — signed envelopes written to `v3/server-config/rtc-signal/<recipientPubkey>/<msgId>`, verified with Schnorr, deduped, TTL-bounded (60s), and tombstoned on consume — used when WSS is down but Gun is up, routed by stable signing pubkey; (3) **manual** — caller-driven bundle exchange (implemented in `WebRTCService`). `sendSignal(target, kind, payload)` returns `false` when no automatic channel exists. `onSignal(cb)` delivers normalized `InboundSignal { kind, remoteId, reply, sdp?, candidate? }`. `currentTier()` → `'wss' | 'gun' | 'mesh' | 'none'`. **All automatic tiers now carry the SAME Schnorr-signed envelope** (`buildEnvelope`/`verifyEnvelope`; body = kind/fromPubkey/fromPeerId/targetPubkey/targetPeerId/ts/msgId/sdp/candidate): the WSS tier is now signature-verified too (closes HIGH-2 — `onWssSignal` rejects forged/tampered/stale offers). New **mesh-relay tier** (`MESH_SIGNAL_TYPE = 'signal-relay'`): when no relay is reachable but ≥1 datachannel exists, the signed envelope is flooded over the mesh (`WebRTCService.broadcastToAll`); `handleRelayEnvelope()` delivers it if `targetPubkey === mine`, else re-floods with a decremented hop (`SIGNAL_HOP_MAX = 4`), deduped via the shared `seen` set — so peers already in the mesh introduce new peers with zero servers. Wired via `WebRTCService.onMessage('signal-relay', …)`. |
| `meshService.ts` | `MeshService` | Auto full-mesh manager. Reconciles every 5s to keep up to 10 direct WebRTC connections to known peers so the mesh is formed *before* a relay drops. Peer sources: WSS live peer list (`WebSocketService.getPeerIds()`, by peerId) and signed Gun discovery announcements advertising the `webrtc` capability (by `signerPubkey`). Re-dial cooldown 30s. Publishes its own `webrtc`-capable announcement every 2min so peers can dial it via Gun even with no live WSS relay, and subscribes live to Gun announcements. Bridges Gun's wire protocol over the datachannels via `GunService.attachWireBridge()` (`gun-wire` messages), so content (polls/posts/comments) replicates P2P with no Gun relay. Default-on unless `interpoll_mesh_enabled` is explicitly `'false'`. `setEnabled()`, `getStatus()`. |
| `keyService.ts` | `KeyService` | Persistent secp256k1 Schnorr key pair, stored in IndexedDB metadata under `'nostr-keypair'`. Auto-generates if missing. Used for block signing and Nostr-style event signing. **This keypair is the portable protocol identity** (Phase 2). Backup/restore: `exportPrivateKey()` (raw hex), `exportMnemonic()` (24-word BIP-39 phrase via `CryptoService.privateKeyToMnemonic`), `importPrivateKey(hex)` / `importFromMnemonic(phrase)`. The 24-word identity phrase is distinct from the 12-word receipt codes. |
| `relayManager.ts` | `RelayManager` | Multi-relay endpoint manager with capability-aware auto-failover. Stores relay list in localStorage (`interpoll_relay_list`) and transport strategy flags (`preferDecentralized`, `allowWssFallback`, `autoSwitch`, TTL/cooldown/probe thresholds). Runtime orchestration prefers fresh signature-verified discovered relays first, then WSS fallback when enabled. Auto-switch safety checks include discovery signature validity, environment-safe protocol validation, freshness TTL, health probe success, and rollback/cooldown on repeated failures. Gun health probes use a browser-safe `no-cors` request; opaque responses are treated as Gun-reachable to avoid false degraded/offline status on cross-origin probes where the browser masks status codes. Relay switching (manual and auto) now rejects only `offline` probes, so browser CORS limits on Gun probes do not block failover when WS/API are otherwise reachable. The manager now hooks into `WebSocketService.onStatusChange()` so reconnect/switch strategy runs during normal runtime (not only in the Resilience page). Uses dynamic imports for `WebSocketService`/`GunService` to avoid circular deps. `recoverFromBlackout(): Promise<boolean>` is a **blackout-only aggressive path** called solely by `ResilienceService`: it reads Schnorr-verified `DiscoveryService.getEntries()` (incl. rendezvous), registers them as discovered relays, probes, and switches to the first healthy one — deliberately bypassing the conservative `allowDiscoveredAutoSwitch` default and the normal `source==='peer'` candidate restriction, justified because during a total blackout the alternative is zero connectivity and every endpoint is already signature- and protocol-verified. Normal-operation `getCandidateOrder()` is unchanged. |
| `resilienceService.ts` | `ResilienceService` | **Resilience orchestrator** (GameOver-Zeus-inspired escalation ladder). Owns no transport logic; detects total **blackout** and escalates in order: (1) `RelayManager.autoFailover()`, (2) gossip refresh (`DiscoveryService.refreshFromGun()`), (3) **rendezvous** reconvergence (`DiscoveryService.publishRendezvous()` + `subscribeRendezvous()`), (4) blackout recovery (`RelayManager.recoverFromBlackout()` dials verified rendezvous-discovered endpoints) + WebRTC mesh (`MeshService`). **Blackout is defined by actual connectivity only** — `!wsConnected && !gunConnected && peerCount === 0` — *not* by an empty address book (the self-seeded local known-server would otherwise permanently suppress it). Escalation past gossip is gated by a `BLACKOUT_GRACE_MS` (30s) continuous-isolation window (`blackoutSince`) so a transient blip doesn't spin up rendezvous. `initialize()` is wired in `chainStore` after `MeshService.initialize()`; subscribes to `WebSocketService.onStatusChange` and polls every 15s. Auto-escalation is gated by `localStorage('interpoll_rendezvous_enabled')` (default on) and re-published every 2min while active. Exposes `getStatus(): ResilienceStatus`, `activateRendezvous()` / `deactivateRendezvous()` (manual override), `setAutoEnabled()`. Consumed by the ResiliencePage "Fallback Rendezvous" card. **Signaling-substrate widening:** each evaluate tick (and on rendezvous activation) `widenSignalingSubstrate()` learns live Gun relays from signature-verified `DiscoveryService.getEntries()` and `GunService.addPeerDynamic()`s new ones (capped at `MAX_LIVE_GUN_PEERS = 8`). Because Gun is the substrate the mesh uses to auto-dial peers, keeping it broad and alive is what lets browser-to-browser stay automatic (no manual QR) as long as any one relay is reachable. |
| `peerReputationService.ts` | `PeerReputationService` | Persistent, time-decaying reliability score per relay/peer endpoint id, in `localStorage('interpoll_peer_reputation')`. `recordSuccess/recordFailure` update an EWMA score in `[0,1]` (neutral 0.5 start); `scoreFor()`, `rank(ids)` (best-first, stable tiebreak), `shouldPrune(id)` (low score AND stale), `snapshot()` for UI. `RelayManager.probeRelay()` feeds success/failure and `getCandidateOrder()` uses `rank` as a priority tiebreaker; `WebSocketService` evicts the lowest-reputation known server first at capacity. Standalone (no service deps) to avoid import cycles. |
| `relayHealthService.ts` | `RelayHealthService` | Relay connectivity diagnostics. Probes WebSocket, GunDB, and API endpoints with latency measurement. Includes Tor Browser detection heuristics and censorship analysis (blocked / reachable / torRequired categorization). |
| `snapshotAutoService.ts` | `SnapshotAutoService` | Automatic local snapshot persistence for offline resilience. `initialize()` starts a periodic auto-save (5 min) + save-on-`visibilitychange`/`pagehide` (**throttled** to the same 5 min — an unthrottled hide-handler meant a full content enumeration every few seconds while alt-tabbing); `save()` runs `SnapshotService.export({ lite: true })` — bounded per-root slice, no relay REST fetch — and stores the latest snapshot in the IndexedDB `metadata` store under `last-snapshot`, **skipping unchanged snapshots** (cheap meta-count signature). `restore()` re-imports it (chain → IndexedDB, content → Gun) so the app works offline and can **re-seed** the network after an outage. Wired from `main.ts`'s deferred block: `restore()` → `useChainStore().loadBlocks()`, then `initialize()`. Paired with a **PWA service worker** (`vite-plugin-pwa`, `registerType:'autoUpdate'`) that precaches the app shell so the app *loads* with no network (verified: app boots from cache with the server down); relay/Gun/API traffic stays network-first (`navigateFallbackDenylist`). |
| `bootstrapInviteService.ts` | `BootstrapInviteService` | First-contact bootstrap helpers for relay recovery. Creates/parses `interpoll-bootstrap://` artifacts (with optional signature metadata and optional peer handoff metadata: source peer id, connected server endpoint, and status counters like posts/polls/block height), validates candidate endpoints, and discovers bootstrap relay candidates from GunDB `server-config` paths. |
| `memoryWatchdogService.ts` | `MemoryWatchdogService` | Monitors `performance.memory` every 30s. Three cleanup levels: light (evict Gun nodes > 5K), aggressive (clear Gun localStorage + deep nodes), emergency (full Gun reset). Periodic light cleanup every 2min even without memory API. Stores/services can register cleanup callbacks via `onCleanup()`. |

## Blockchain

| File | Class | Purpose |
|---|---|---|
| `chainService.ts` | `ChainService` | Block creation, signing, validation, chain init/reset. Each block includes `previousHash`, `voteHash`, Schnorr `signature`, and `currentHash`. Genesis is now deterministic/legacy (shared timestamp+hash, no per-device signature) so fresh clients converge on the same index-0 block. Incoming block validation enforces strict hash/signature/pubkey formats, bounded timestamp skew (future skew + large backward skew guard), action metadata constraints, and explicit genesis validation; unsigned legacy blocks are tolerated only in `allowLegacy` validation paths used for sync/history checks. |
| `cryptoService.ts` | `CryptoService` | SHA-256 hashing (`@noble/hashes`), Schnorr sign/verify (`@noble/curves`), BIP-39 code generation utilities (used for receipt verification codes), browser fingerprinting. Also `privateKeyToMnemonic()` / `mnemonicToPrivateKey()` — a lossless round-trip between a 32-byte Schnorr private key and a 24-word BIP-39 phrase (bip39 entropy encoding), used by `KeyService` for identity backup/restore. |
| `voteTallyService.ts` | `VoteTallyService` | **Verified vote tally (CRITICAL-2 mitigation).** UI poll counts come from forgeable Gun values; this service aggregates the Schnorr-signed kind-101 vote events that already broadcast across the network (previously verified-then-discarded in `chainStore.handleNewEvent`) into a per-poll, per-option tally **deduped by signer** (one vote per pubkey, latest wins). `ingest(event)` (hot path, assumes verified), `ingestUntrusted(event)` (verifies first — used by the Gun `events` backfill in `initialize()`), `getVerifiedTally(pollId)` / `getVerifiedTotal(pollId)`, and `looksInflated(pollId, reportedTotal)` (flags when the Gun total materially exceeds the verified count). Persisted to the IndexedDB `metadata` store. Surfaced in `PollCard.vue` as a "N verified" badge (turns to a warning when inflated). Honest scope: a client only holds events that reached it, so the verified tally is a trustworthy **lower bound**, not global consensus. |
| `postVoteService.ts` | `PostVoteService` | **Derived post vote tallies.** Votes are per-user nodes `postVotes/<postId>/<userId>` counted by `foldVotes()`; the counters on the post node are an advisory mirror only. Replaces the read-modify-write on `upvotes`/`downvotes` that lost a vote whenever two landed inside one round trip. `castVote()` toggles and returns `{ tally, myVote }` — callers reconcile against `myVote` rather than predicting the outcome. `clearVote()`, `getMyVote()` (falls back to the pre-migration `votes/vote_{userId}_{postId}` key, or `votes/vote_{userId}_poll_{pollId}` for polls), `getTally()`, `subscribeTally()`. Legacy totals are frozen once as an immutable baseline (`voteBaselineUp`/`voteBaselineDown`/`voteBaselineAt`) and a migrated voter's node carries `baselineType` so their old vote is not double-counted. **Also serves poll content votes**, keyed by poll id — only the baseline differs: `baselineNode()` resolves a `poll-` id to `polls/<id>`, because `posts/<id>` for a poll holds only its category patch and freezing a baseline from it would reset every existing poll's score to zero. See "Vote counters are derived, never accumulated" below. |
| `voteTrackerService.ts` | `VoteTrackerService` | Device fingerprint (canvas + browser properties → SHA-256, stored in IndexedDB metadata as `'device-id'`). Tracks `vote-records` in metadata to prevent duplicate votes. **Dedup identity precedence (Phase 2):** `getVoterIdentity()` returns `{ deviceId, pubkey }`; `hasVoted`/`getMyVotes` match a stored record when the pubkey matches (both present) **or**, falling back, the deviceId matches — mirroring the relay's `identityKey` precedence (`pollId:pubkey` else `pollId:deviceId`) so client and relay agree on "same voter". Legacy records (deviceId only) still block re-votes; new records store both. |
| `powService.ts` | `PowService` | Client-side hashcash proof-of-work. Requests a challenge from the relay via WebSocket (`request-pow` → `pow-challenge`), including the current identity username claim for issuer-tier challenge/rate-limit handling on the relay. Solves with SHA-256 mining (async loop with event-loop yielding), and returns `{ challengeId, nonce }` ready to attach to content messages. Concurrent calls are serialised via an internal queue. Used automatically by `WebSocketService.broadcast()` for PoW-required message types. |
| `integrityService.ts` | `IntegrityService` | Seals outgoing state-mutating messages with integrity metadata (`_sig`, `_pub`, `_hash`, `_pow`, `_ts`, `_nonce`). Pipeline: canonicalJSON → Schnorr sign → SHA-256 hash → hashcash PoW → freshness fields. Mirrors backend verification order from `shared-validation/pow.js`. PoW difficulty is per-message-type; exempt types (ping, pong, RTC signaling, etc.) are skipped. Also includes `verifySealedPayload()` for client-side verification of signed discovery/transport envelopes (hash/signature/PoW/freshness). |

## GunDB Domain Services

| File | Class | Purpose |
|---|---|---|
| `pollService.ts` | `PollService` | Poll CRUD, invite code generation/validation/consumption, vote recording in GunDB. **Content votes (up/down on the poll card) delegate to `PostVoteService`** — `voteOnPollContent()` returns `{ upvotes, downvotes, score, myVote }`, plus `getPollContentTally()`, `getMyPollContentVote()`, `subscribeToPollContentVotes()`. The previous implementation was the read-modify-write counter that scheme replaces: it read `poll.upvotes`, adjusted it and wrote it back (two votes inside one round trip lost one, a stale read reverted votes already recorded), and cleared a vote with `put(null)`, which Gun does not propagate reliably, so toggled-off poll votes kept coming back. Option voting is unrelated and still lives here. Schnorr-signs polls on create (`authorPubkey`, `contentSignature`). Community/all-poll subscriptions use hydration-first loading with batch processing plus soft/hard timeouts to avoid startup hangs while preventing startup content from being treated as "new". `loadPoll()` is Gun-first for live vote totals; API fallback is metadata-only (question/options labels) and does **not** ingest API vote counts, preventing stale backend totals from bouncing local/Gun-confirmed votes. When the global poll root is missing or late, reads can now fall back to the known community-scoped poll path, hydrate options from either scope, and warm the root cache so newly created community polls do not disappear and community-routed votes can still resolve against live Gun data. When global poll options are missing during reload, it also falls back to community-scoped poll options before dropping the poll, which prevents empty poll lists caused by partial Gun hydration ordering; if Gun still yields only a partial shell, read flows can fall back to a fresh offline local backup instead of returning null. Community subscriptions now normalize missing `communityId` fields to the subscribed community id before emitting polls, preventing transient partial root records from moving polls out of community feeds. Poll option voter lists are normalized from Gun-safe object storage back into arrays for the app, and voting rewrites the full options map (global + community copy) so option order and vote counts stay aligned. Private poll invite codes are stored both by index and uppercase code key; `validateInviteCode()` checks availability, `consumeInviteCode()` creates a short-lived reservation token and verifies ownership before voting, `finalizeInviteCode()` permanently marks the code used after chain success, `releaseInviteCode()` clears only the caller's own reservation if voting fails before the chain write, and `queueInviteCodeFinalization()` / `flushPendingInviteCodeFinalizations()` persist best-effort finalize retries in localStorage so a post-chain finalize glitch does not silently reopen the code forever. Poll create/read/vote now include same-device local durability fallback (IndexedDB metadata) for degraded relay conditions, but local fallback reads are now offline-only with backup freshness TTL and deletion tombstones to avoid stale/deleted poll resurrection while online. Local backup fallback is disabled for mutating paths (like vote) so writes cannot proceed from stale cached-only poll state. Poll creation now embeds options directly in the root/community poll shell write as a redundancy path, treats dedicated options-child write timeouts as soft failures, and `loadPollOptions()` falls back to inline shell options only after trying live options hydration; this prevents poll creation failures caused by flaky Gun ACKs on `...get('options').put(...)` while reducing stale reads. Root and community poll-shell writes now use timeout-with-verification fallback plus multi-attempt repair retries: after timeout, writes are retried with merged current state and re-verified before failing, which significantly improves propagation on slow relays without clobbering concurrent updates. Poll creation and vote confirmation time budgets were increased further for high-latency relays, while still requiring explicit post-write confirmation before reporting success. Vote writes now normalize selected option IDs against known poll options before write/confirmation and use timeout-tolerant writes with explicit confirmation and retry writes on both root and community paths, using fresh options snapshots per retry so transient lag does not fail otherwise-valid votes or overwrite concurrent voters; once root confirmation succeeds, slower community-path reconciliation continues in the background so UX is not blocked by secondary-path lag. Timeout-tolerant writes no longer emit unconditional console warnings when an ACK is late; failures are now surfaced only if post-write confirmation cannot be established. Private invite-code list writes and `inviteCodesByCode` writes now use timeout-tolerant writes plus explicit read-back confirmation retries (with chunking for by-code writes), so high-latency relays cannot silently drop entries during large private poll creation; search indexing is timeboxed and uses credentials only for same-origin API calls so indexing outages/CORS mismatches cannot block poll creation success. Local poll backup persistence is serialized through a write queue and skips unchanged snapshots using a normalized signature check to avoid repeated metadata rewrites from read-heavy paths. Poll creation diagnostics can be enabled from console via `localStorage.setItem('interpoll_poll_debug', 'all')` (or categories: `create,writes,index,ui`) to log write ACK timing, indexing lifecycle, and create flow checkpoints. Encrypted polls are now written redacted from the first Gun write (`🔒 Encrypted Poll`/placeholder options/`authorName='encrypted'`) and include `encryptedContent`/`authTag` immediately, so plaintext never lands on shared roots before encryption. Encrypted poll creation now hard-fails if key-based encryption fails, and encrypted polls skip plaintext search indexing. Poll creation now treats poll-policy registration as best-effort: it attempts relay registration first, but still propagates writes to Gun/community paths if the relay rejects/unavailable, then retries policy registration in the background with backoff so decentralized propagation is not blocked by relay policy bootstrap timing. **Relay persistence verification:** Gun put ACKs fire on local storage acceptance and read-backs are served from the local graph, so neither proves the relay holds the data. `createPoll` therefore finishes with `verifyRelayPersistence(pollId)` — an independent `GET {gunRelayBase}/db/soul?soul=v3/polls/<id>` read against the relay's DB mirror (retried up to ~8s; falls back to `GunService.getPeerStats().isConnected` when the endpoint is unreachable) — and sets `poll.relayConfirmed`. UI callers (e.g. `CreatePollPage`) surface a 'saved locally, relay unconfirmed' warning instead of an unqualified success when it is false. **Background republish:** Gun never retro-syncs puts made while a relay wire was dead, and a rate-limited relay can silently drop messages on an *open* socket, so `startRepublishLoop()` (kicked from `App.vue` on mount, on `GunService.onReconnect`, and after an unconfirmed create) sweeps fresh local poll backups every 2 min, re-verifies each via `/db/soul`, and re-puts unconfirmed ones through `warmPollCache` with the same encrypted-poll redaction as `createPoll` (max 5 attempts per poll, TTL-bounded). Note the relay's MySQL mirror can lag tens of seconds behind its Gun graph, so a single short verification window can report a false negative — the loop re-verifies before and after each re-put, which is idempotent under Gun's merge. `App.vue` also runs a 60s wire watchdog (`getPeerStats().isConnected` → `GunService.reconnect()`), complementing the visibilitychange-only check. |
| `communityService.ts` | `CommunityService` | Community CRUD in GunDB. IDs are derived from lowercased name: `c-{slug}`. Signs community creation with Schnorr (via `CryptoService`/`KeyService`) for anti-sabotage; includes `verifyCommunitySignature()` to check integrity. Supports private encrypted communities via `createPrivateCommunity()` (AES-256-GCM encrypted metadata, password-derived or invite-only keys), `decryptCommunityMeta()` (decrypt using stored key), and `joinPrivateCommunity()` (join with invite key or password). `subscribeToCommunitiesLive()` now forwards repeat updates so member-count and metadata changes are not dropped after first load, but avoids repeated per-update `rules` child lookups by reusing inline/cached rules and keeping a single per-community `rules` subscription for cache sync. ## Memory pressure: `trimCaches(level)`

Services that hold per-entity caches expose a static
`trimCaches(level: 'light' | 'aggressive' | 'emergency')`: `PostService`,
`CommunityService`, `TrustService`, `ModerationService`. These are registered with
`MemoryWatchdogService.onCleanup()` in `main.ts` — the watchdog's callback registry
had no subscribers before, so every pressure level only evicted the Gun graph while
app-level caches grew unbounded for the session.

Convention for a new `trimCaches`:
- `light` — `prune()` only (drop already-expired entries), never touch live data
- `aggressive` — shrink or clear derived/lookup caches
- `emergency` — clear everything re-derivable

Only cache *data*. Never evict subscriptions, in-flight promises, or unsubscriber
maps: dropping those leaks the underlying listener rather than freeing anything.
Backing stores are `BoundedMap`/`BoundedSet` (see `src/utils/copilot-utils.md`).

## Search indexing is server-side only

Clients do **not** index content. `gun-relay/gun-relay-enhanced.js` indexes posts
and polls from its own Gun `put` hook (`maybeIndexNode` → `indexSearchRow`), writing
`search_index` directly on its MySQL pool. Anything reaching the graph is indexed
regardless of whether the author was signed in.

Do not reintroduce a client-side `POST /api/index` call. That endpoint is gated on
`API_INDEX_SECRET`, which a browser cannot hold, so such calls only ever returned
401 into a swallowed warning — while paying for a PoW `IntegrityService.seal()` on
the publish path. `SearchService` deliberately has no `indexContent()` method.

## Vote counters are derived, never accumulated

Post and comment vote totals are **counted from per-user vote nodes**, not stored as
mutable numbers. `postVotes/<postId>/<userId>` and `commentVotes/<commentId>/<userId>`
are keyed by voter, so concurrent voters write disjoint keys and cannot clobber one
another. Do not add a read-modify-write of `upvotes`/`downvotes`/`score` anywhere:
under Gun's last-write-wins merge, two votes inside one round trip both read N and
both write N+1, and one silently disappears. That is what this replaced.

Clearing a vote writes an explicit `'none'`, never `put(null)` — Gun deletes do not
propagate reliably, and the old post toggle depended on exactly that.

The `upvotes`/`downvotes`/`score` fields still present on a post/comment node are an
**advisory mirror**, written by the last voter from a correct tally so a card can
render before its vote set loads. Any peer can echo a stale copy of them. Every read
path prefers the derived tally; `postStore` overlays the derived value permanently
once it has one.

**Legacy counters (posts):** totals predating the change are frozen onto the post as
an immutable baseline (`voteBaselineUp`/`voteBaselineDown`, guarded by
`voteBaselineAt`) the first time anyone votes, and the tally reports
`baseline + derived`. It is written once and never mutated, so it introduces no
race. A voter who had voted under the old scheme is already inside that baseline;
their new node records `baselineType` and the fold subtracts one for it. The whole
rule is the pure `foldVotes()` in `postVoteService.ts` — tested in
`unit_tests/postVoteTally.test.ts`. Comment tallies take a simpler route: they fall
back to the stored counters only while *nobody* has voted under the new scheme, so
an old comment's total drops to the new count on the first vote.

`PostService.getPostForCounterUpdate()` still exists, but only to supply the
surrounding post fields to merge a tally into — counts no longer flow through it, so
a stale read there can no longer revert a vote.

**Who decides a toggle:** `postStore.toggleVote()`, once. The views used to decide
"vote or unvote" from their own `localStorage` sets while the service decided the
same question from the graph; when the two disagreed the click inverted, rendering
+1 while the write did -1. Vote state now lives in `postStore.myVotes` (persisted as
`my-post-votes-v1`, migrating the old `upvoted-posts`/`downvoted-posts` sets) and is
corrected by whatever the graph reports back.
